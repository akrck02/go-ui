2. Window tests: drive an interface in go test, with no display

Status: in review · Author’s approval: proposal ☑ (2026-10-21) plan ☑ (2026-10-21)

Why

Go UI’s own tests already drive interfaces frame by frame: a private harness in ui_test.go makes an input.State of 800×600, moves a fake mouse, runs Begin, the interface and End, and reads where an element was laid out. Programs built on Go UI (an editor, a settings app, a game’s menus) cannot use it: it is private, it uses a fake measurer of the test file, and it finds elements by hashing a label by hand. Each program ends up writing its own copy, or not testing its interface at all.

Like Go’s net/http/httptest, Go UI should ship a small public package for that: open a pretend window, press, type and wait in it, and ask what it shows. No display, no OpenGL, no cgo, so it runs in any go test and in CI.

What

The package is called uitest (chosen by the author: tests of a Go UI interface, as httptest tests a server). Its tests are written against an interface made only for them: a lighthouse keeper’s log with a button, a check box, a text field and a dialog.

Id Requirement Check

Out of scope

  • A picture of a frame without a display: the viewer of R12 paints recorded draw lists in a real window, which needs a display.
  • A PNG of a frame and golden images (the author’s decision): Go Renderer has no software painter today (its software/ package is a stub), so there is no way to paint a frame without a display. Once Go Renderer can paint a draw list into an image.RGBA, a Picture method and a golden-file helper are a separate proposal. DrawList (R8) is what tests read until then.
  • Testing through a real backend window (window/): this package drives ui.Context and input.State directly; the backends keep their own tests.
  • Recording a session by hand and playing it back.
  • Game pads, and the screen-reader actions beyond what R6 reads (they already have ReaderPress and friends).

Design

The pieces

uitest/ is a new package at the root, beside window/. It imports ui, draw2d and input only; ui never imports it. Its files, one part each:

File What it holds
window.go Window: a *ui.Context, an *input.State, the interface function, the clock. New(build, options...), Frame, Frames(count), Resize, Context, State (an escape hatch for what the package does not cover yet)
options.go Size(width, height), Scale(factor), Theme(theme), Measurer(measurer): functional options, so New(build) works with nothing else
measurer.go FixedMeasurer: each character half the text size wide, as the private fakeMeasurer does today; the default
clock.go the window’s clock, set into input.State.Now; Wait(duration) moves it and runs the frames that fall in that time at a fixed step (frameDuration, one sixtieth of a second)
pointer.go MoveTo, MoveToElement, Press, Release, Click, DoubleClick, Drag, Scroll
keyboard.go PressKey, HoldKey, ReleaseKey, Tab, ShiftTab, Type
touch.go TouchDown, TouchMove, TouchUp, Tap, LongPress
find.go Element(label) and ElementIn(scope, label) return an Element (label, Rect, Visible, Focused, Pressable); Texts(); DrawList()
errors.go the codes, at the top, and one constructor each
example_test.go, *_test.go the tests named in What, beside the code

Every action is one or more whole frames: an action changes the input state, runs Frame, and returns an error when its target is missing. Click is press, frame, release, frame, because a control in Go UI answers on release and needs the frame between.

Finding elements

The package reads the screen-reader tree (ScreenReaderNodes), which already gives each control its ID, label, rectangle (already clipped by scroll areas) and whether it can be pressed. The test window switches the screen reader on when it is made. Two small public additions to ui are needed, both generic and useful to any program:

  • (*Context).FocusedID() ID: which control has the focus. Today it is private.
  • AccessibleNode.Hidden, or an equivalent rule: a node under a modal layer is not visible. If the tree already leaves those nodes out, nothing is added; T2 checks which.

Texts() walks the draw list for TextKind commands, so it also finds text that is not a control (a heading, a status line).

Errors are a small type: Error{Code, Message} with Code a string constant, compared with errors.Is against a sentinel per code (uitest.ErrorElementNotFound), so returning one only allocates when a test fails. Codes: uitest.element-not-found, uitest.element-ambiguous, uitest.element-not-visible, uitest.element-not-pressable, uitest.invalid-size.

Go UI’s own tests

Tests inside package ui cannot import uitest: uitest imports ui, and that would be a cycle. So the tests that only use public behaviour (click a button, type in a field, Tab through controls) move to package ui_test files and use uitest; the tests that read private state (ui.previous, the focus order, memory) keep a much smaller private harness. T6 lists which is which before moving anything.

The results viewer (R12)

  • Recording (uitest/recording.go): a window made with the Test(t) option and the environment variable UITEST_RECORD set to a folder keeps, for each frame, a copy of the draw list’s commands, the pointer, the fingers, the action that ran it (Click "Save") and the rectangle of the element that action found. Errors returned by the package are kept too. At the end of the test (t.Cleanup) it writes one JSON file per test into that folder, with the test’s name and whether it failed. With the variable unset, Test(t) only remembers the name: no copy, no file. Pictures in a draw list are kept by size only (a grey box in the replay).
  • The program (cmd/uitest/): go run ./cmd/uitest ./... makes a fresh folder, runs go test with UITEST_RECORD set and the arguments given, then opens a window with the results. Its logic (results.go: load the folder, sort failed tests first, step through frames) is apart from its look (view.go), so the logic is tested with uitest itself, headless.
  • The look: a side list of tests as Selectable rows with a check or cross icon and a Chip for each error code; the chosen test in a card with its name, its messages and the replay: the recorded draw list painted with Paint, scaled to fit, the pointer as a ring, a press as a filled ring, and the found element outlined in the theme’s FocusRing. Buttons and a Slider step through the frames. (The arrow keys were dropped while building: ui.Context gives a program no public way to read a key outside a scene.)
  • Not taken: an HTML report (the author asked for a Go UI window); recording always (it would cost every go test).

Not taken

  • Finding elements through a new private-state accessor on Context (a public map of laid-out rectangles): it would add a field read only by tests (against R11). The screen-reader tree is already public, already clipped, and already labelled.
  • Methods that take *testing.T and fail the test themselves: shorter tests, but the author asked for errors with codes and no panics, and a returned error also works outside go test.
  • Real time with time.Sleep: slow and flaky in CI.
  • A PNG of a frame: no software painter yet (see Out of scope).

Result

Built on feature/window-tests, one commit per task:

  • Package uitest (R1–R8, R11): New with Size, Scale, Theme, Measurer, Test; Frame, Frames, Wait; the pointer, keys, typed text and touch; Element, ElementIn, Texts, DrawList; errors with seven codes in uitest/errors.go. One public addition to ui: Context.FocusedID. AccessibleNode.Hidden was not needed: the screen-reader tree already leaves out what is behind a dialog, and a text covered by a higher layer is found not visible.
  • Go UI’s own tests (R9): five tests moved to uitest; the rest keep the private harness because they read private state.
  • ExampleWindow and the guide docs/4-guides/11-testing-an-interface.md, with its reference page (R10).
  • Recording and the viewer cmd/uitest (R12).

Checks run: gofmt -l . prints nothing; go vet ./... and go test ./... pass; every test named in What exists and passes; go list -deps of ui has no uitest. The viewer was run once under Xvfb with Mesa (-capture) on two made-up tests: it drew the list, the error card and the replay.

Not built, or different from the plan:

  • The arrow keys in the viewer: ui.Context has no public way to read a key outside a scene.

  • A plain line of text (not a control) is found from the draw list, because the screen reader joins the texts of one box into one node; such an element is never Focused or Pressable. The not-found message lists the screen reader’s labels, which may show joined texts.

  • Test(t) reports a recording it could not save with t.Error: the one place the package fails a test itself, and only while recording is on.

  • The replay (fixed after the first capture): the recording keeps each text’s measured width and the theme’s background; the viewer shrinks a line its fonts would paint wider, never enlarges the window, and draws the pointer only once it has been somewhere. Shadows are redrawn from their recorded size, only roughly.

  • After each input the window runs one more frame and any frame asked for at once, as Go Renderer’s on-demand loop does; found while trying uitest on go-engine’s editor, whose workspace bar is drawn after the page it changes.

For a person to review: all of it is AI-written and pending review. The viewer’s look on a real display (light and dark), how it feels to step through a long test, and whether uitest is the API go-engine’s editor wants, by writing one of its tests with it.
